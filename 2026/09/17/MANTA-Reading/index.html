MANTA 论文阅读笔记

发表于2026-09-17|更新于2026-10-16|论文阅读

0、核心总结

MANTA核心逻辑：包括内外两次循环

内循环（每道题）：

  1. Planner：读长期文稿，分析任务类型/属性/失败风险 => 输出紧凑 JSON 计划
  2. Orchestrator：展开成完整拓扑 → 校验（组成员唯一、挂载无环、角色合法、预算内）→ 校验失败则在任何 AI 被实例化之前拒绝，退回 fallback
  3. 跑第 1 轮
  4. Trace Auditor 扫过程 → 报 flag
  5. Controller 门控：
    • 智能体协作无异常 → 直接 Finalizer 投票出答案
    • 有 medium/high 可修复 flag → Planner 提一个变异（≤3 op） → Orchestrator 在副本上应用并校验 → 重指向 context controller（状态零迁移）→ 跑第 2 轮
  6. Finalizer 在所有轮次的候选上投票 → 最终答案

**外循环（每 12 次运行）：**更新长期PlayBook

一、这篇论文在解决什么问题？

**背景：**多智能体协作解决问题变得热门。

问题： 多智能体的协作拓扑都是事先设计好、写死的。任务一开始，架构就冻结了，中间发现不合适也无法修改。

**例子：**两个人各查一半资料。结果跑起来发现，其中一个拼命在工作，另一个却很闲。但架构是死的，只能硬着头皮跑完。

思路：能不能让这套「组织架构」在解题过程中自己动手改？

二、MANTA 是怎么做的？

Step1：组队

拿到题目后，系统先想：「这题需要几个人？什么结构？要不要一个专门检查的？」

比如一道需要查很多方向的题，它可能决定：1 个组长 + 3 个查资料的 + 1 个核对证据的。

Step2：跑一轮试试

按这个架构干一轮活，互相互传消息。消息是压缩成一句话摘要传的，不是把整段对话倒给对方。

Step3：检查过程有没有毛病

跑完后，有个「监工」专门看过程有没有问题。它盯的是这些信号：

  • 同一个动作被两个人重复做了一遍（比如两个人同时去改同一个文件）
  • 某个分支卡住了、啥也没产出
  • 有人收集了资料，但汇总的时候根本没交上去
  • 大家太快就同意了，但其实心里没底、还有没解决的问题
  • 该有人验证的地方却没人验证

特别注意：这个监工只判断过程干不干净，不看答案对不对。

Step4：最多改一次结构

如果监工发现毛病，系统最多改一次（这是硬规定），而且改动不超过 3 个小操作。可以改的东西有：

能改什么 例子
加人 / 拆小组 把那个过载的人变成一个小组的小组长，给他配几个手下
换拓扑 从「星形」换成「链式」
加/删联系 让两个本来不直接说话的智能体直接沟通
改信息可见性 让某个智能体能看到全部资料

改完之后再跑最后一轮，出答案。

三、两个「笔记本」：它是怎么记住经验的？

这叫 Playbook（战术手册），分两本：

第一本——这一局用的（短期） 记着「这一轮用了什么架构、出了什么毛病、改了什么」。作用是别重复犯错：同一道题里不会刚改完又改回去。

第二本——长期积累的（长期） 跨题、跨领域攒下来的通用经验，写成一份 markdown 文档。里面记的是类似这样的话：

「没有工具、纯推理的题，用『投票制』比用单个 AI 好：投票制 35 次全干净，单个 AI 6 次全出毛病。」

「任务有先后依赖关系（后一步得等前一步），用链式而不是并行，不然大家各看一块、拼不起来。」

「要改外部状态的动作（写文件、发消息），必须只有一个人做，不然会重复执行。」

每 12 次运行，会让 AI 把这份文档重写一遍，把新经验加进去、把矛盾的删掉。

四、最关键的一条规矩：绝对不告诉系统答案对不对

这是整篇论文最值得称赞的地方。

系统内部任何组件——组队的、监工的、写笔记本的——都不许知道 benchmark 的正确答案。 监工只能看到「过程干不干净」，不能看「这答案得分多少」。

为什么这么做？ 因为如果让它看答案，它学到的就是「什么样的架构在这道题上得分高」——那是背答案，换个领域就没用了。

代价：学习信号变弱了。但好处很大——实验证明，这套经验能跨领域用。
